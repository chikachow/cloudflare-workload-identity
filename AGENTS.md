# Repository guidance

## Workflow

1. Inspect the worktree, affected code, tests, and references triggered below. Identify the requested outcome and governing contracts; preserve unrelated modifications and untracked files.
2. Choose the simplest cohesive design for the affected concern, including callers and lifecycle transitions. Assess existing and proposed designs against the same required behavior and public contracts; distinguish those obligations from implementation choices. Justify retaining, adding, or removing abstractions and safeguards by concrete requirements, weighing benefits against migration, regression, review, and maintenance costs.
3. Resolve routine choices from repository evidence and carry prior agreement forward. Ask when an unresolved requirement materially affects compatibility, recovery, scope, or authorization; continue independent work while awaiting the answer. Reviews and plans call for analysis, not unrequested implementation.
4. Before choosing checks, read [validation scope](CONTRIBUTING.md#validation-scope). Review the final diff against the requested outcome and affected contracts. For implementation tasks, resolve actionable in-scope findings and rerun affected checks before completion. For review tasks, report evidenced findings, distinguishing defects, unmet outcomes, contract questions, and optional improvements.
5. Report each material requested outcome with supporting evidence, checks performed, and limitations. A handoff with required verification or review pending is incomplete: identify the remaining work, the specific blocker, safe scoped alternatives considered, and the input or access needed. Commit, push, publish, or change remote state only within the user's authorization.

## Contracts and runtime boundaries

- Preserve established domain and protocol terminology. For domain terms, public names, token semantics, or consumer-facing explanations, read [CONTEXT.md](CONTEXT.md); consult the [terminology decision](docs/research/oauth-oidc-terminology.md) when the standards rationale matters. Rename internal symbols when a concrete correctness or comprehension benefit justifies the change.
- For issuance, audience policy, RPC errors, discovery responses, key validation, caching, or rotation, read the affected sections of the normative [workload identity profile](docs/workload-identity-profile.md). Resolve disagreements between that contract, tests, and implementation explicitly; passing current tests alone does not establish the intended behavior.
- Validate runtime input and bindings at their owning boundaries even when TypeScript supplies a type; pass established guarantees inward without redundant validation. Keep authorization before signing-secret access and preserve the authorized subject and audience across asynchronous key loading. Scope copying or immutability to values whose later security decisions depend on stability; follow the profile's distinct closed and extensible shapes rather than rejecting all unknown fields.
- Shared profile rules currently live in `packages/workload-identity-profile`; Cloudflare entrypoints live in the Workers. Structural changes must preserve shared policy consistency, required package APIs, valid deployed entrypoints, and compatibility with the configured runtime; these obligations do not require retaining the current filenames or layout.
- For Wrangler, Vitest integration, entrypoints, generated bindings, or build configuration, read [tooling and build verification](CONTRIBUTING.md#tooling-and-build-verification). For installation or dependency updates, read [dependency tooling](README.md#dependency-tooling) for package-manager setup and dependency policy.
- For deployment, resource exposure, signing keys, or source-pin changes, read the [source and deployment boundary](CONTRIBUTING.md#source-and-deployment-boundary) before acting.

## Evidence and documentation

- Match evidence to the claim: source explains implemented logic, execution establishes observed behavior, and current primary documentation establishes external contracts. State remaining inferences; distinguish static walkthroughs from observed executions and local results from deployed behavior.
- Keep repository guidance useful without personal agent configuration. Maintain one authoritative definition per policy: this file owns agent workflow, [CONTRIBUTING.md](CONTRIBUTING.md) owns verification, the profile owns wire/security contracts, and `CONTEXT.md` owns vocabulary. Use concise summaries and task-triggered pointers elsewhere; update owners whose meaning changes and keep evaluation history and completed plans with their change records.
- Add preventive rules when a concrete, consequential failure threatens an established contract and the rule has a clear trigger and permitted path. Treat broader workflow heuristics as provisional until experience supports them; revise or remove rules that add friction without demonstrated benefit.
